## DEC-001：本地优先且无登录

- 决策：不设计登录、注册、云账户或用户 Profile。
- 原因：产品定位是本地桌面 AI Agent 应用。
- 影响：左侧栏底部展示 Aestival 品牌菜单，不展示用户头像和用户名。
- 来源：用户需求、`docs/设计方案/README.md`。

## DEC-002：shadcn/ui 作为强制组件层

- 决策：已有 shadcn/ui 组件不得用手写基础组件替代。
- 原因：保持行为、样式、可访问性和跨工具实现一致。
- 影响：新组件先查本地组件与 registry；业务组件只做组合。
- 来源：用户需求、`AGENTS.md`、组件覆盖矩阵。

## DEC-003：Card 克制且不嵌套

- 决策：允许使用 Card，但它不是默认布局；禁止 Card 套 Card及视觉卡片嵌套。
- 原因：减少层级噪声，避免管理页面退化为卡片墙。
- 影响：优先使用普通分区、Item、Separator、列表、表格、Tabs、Accordion、Collapsible 和 Resizable；指标默认使用指标带。
- 验收：单独执行卡片嵌套与过度卡片化审计。
- 来源：用户补充要求、`docs/设计方案/01-视觉系统与窗口布局.md`。

## DEC-004：窗口与面板布局

- 决策：默认左侧栏 + 主内容；右侧栏按需形成第三列；底部面板是垂直分割。
- 原因：兼顾桌面信息密度与主内容最小宽度。
- 影响：使用 Resizable，并提供收起、恢复和窄窗口降级。

## DEC-005：统一右键系统

- 决策：全局禁用浏览器原生右键，按区域使用 shadcn `ContextMenu`。
- 原因：保证菜单图标、快捷键、分组、多级菜单和桌面体验一致。
- 影响：Monaco、终端和输入框也要提供区域专用菜单。

## DEC-006：跨会话同步

- 决策：所有模型、工具和会话必须通过本目录同步任务、状态、决策、变更和风险。
- 原因：后续功能可能由不同 AI 工具跨会话实现，聊天历史不能作为唯一上下文。
- 影响：任何实质工作结束前都要更新同步文档；任务需要唯一 ID 和负责人。

## DEC-007：中文文档

- 决策：项目约束、设计、进度、决策、风险和交接文档使用中文。
- 原因：降低跨模型理解偏差，符合项目界面语言。
- 影响：标准 API、库名、代码标识符保留英文。

## DEC-008：设计先行

- 决策：当前阶段先完成并评审 UI 设计，不提前实现 UI。
- 原因：用户明确要求先写设计方案。
- 影响：UI-001 及其后任务必须等待用户明确授权。
- 状态：已被 DEC-010 替代。

## DEC-009：外部消息连接安全边界

- 决策：Telegram、飞书、Discord、钉钉、微信和 QQ 作为设置中的外部消息连接，由本地 Aestival/后台服务接收和回复；它们不是 Aestival 账号系统。
- 默认：私聊采用配对，群组关闭；启用群组后使用允许列表并要求提及。访问控制使用平台稳定 ID，会话按平台、连接实例、来源和话题隔离。
- 权限：外部代理请求继续使用现有审批引擎；远程只能在显式启用后由连接所有者批准一次性低/中风险动作，高风险授权和权限扩大只能在桌面端完成。
- 数据：渠道 Secret、扫码会话与原始 Authorization 进入本地安全存储或 Secret 引用，不进入普通 Zustand、未脱敏日志或导出。
- 原因：外部入口扩大攻击面，但用户仍需要从常用消息平台安全地控制和使用 Aestival。
- 来源：用户需求、`docs/设计方案/08-任务与设置.md` §5。

## DEC-010：进入 UI 与桌面窗口外壳实现

- 决策：从 UI-001、BE-001 开始实现前端 UI、Mock 交互和 Wails 桌面窗口外壳。
- 边界：允许编写与 UI 交互、窗口尺寸、标题栏、面板和前端状态有关的代码；模型、工具、知识库、文件、任务调度等业务服务继续暂缓。
- 数据：当前使用明确标记的 Mock 数据与前端状态，不伪造网络、模型、文件写入或计费成功。
- 原因：用户在 2026-07-25 明确授权进入代码实现，并要求后端业务逻辑待后续讨论。
- 来源：用户当前任务。

## DEC-011：文本选择边界

- 决策：应用外壳、标题栏、侧栏、导航、工具栏、菜单和按钮默认禁止文字框选；标题栏拖动区使用普通箭头光标。
- 例外：消息正文、文档/代码预览、输入与可编辑区域、Monaco、终端和日志等需要复制内容的表面必须显式恢复文本选择，并保留组件自有的选区能力。
- 原因：避免标题栏拖动起步和普通界面操作误触文字选区，同时不影响阅读、编辑、复制代码与终端输出。
- 来源：用户当前任务、`docs/设计方案/01-视觉系统与窗口布局.md`、`docs/设计方案/03-全局交互与右键菜单.md`。

## DEC-012：单一全局标题栏

- 决策：当前页面、会话或文件名称只允许显示在窗口最上方全局标题栏的主内容段。侧栏展开时，名称位于侧栏边界右侧并与主内容左缘留白对齐，侧栏材质段只保留原生窗口控件与侧栏开关；侧栏收起时，名称移动到窗口安全区与侧栏开关之后。
- 内容边界：主内容区不得重复同名 `h1`，不得使用带背景、底边或固定整行布局的页面 Header 形成第二条标题栏；Breadcrumb、内容说明、状态、主动作和不重复页面名称的章节标题仍可按普通内容分区呈现。
- 原因：消除全局标题栏与页面内部页头并存造成的层级重复，保持桌面窗口结构统一。
- 来源：用户当前任务、`docs/设计方案/01-视觉系统与窗口布局.md`、`docs/设计方案/02-信息架构与导航.md`。

## DEC-013：会话归档与项目边界

- 决策：归档只作用于单个或批量会话，项目本身不支持归档，不在项目行提供归档按钮。
- 侧栏：会话行的 hover/选中背景与项目行等宽，内容保持层级缩进；会话 Hover 时显示归档和更多两个图标，归档先经 `AlertDialog` 确认。
- 消息：消息操作按钮只在 Hover 或操作按钮键盘聚焦时显示，浮动在消息内容边界外，不增加 Bubble 或消息本体高度。
- 原因：保持项目容器与会话记录的状态职责清晰，并避免操作按钮挤占标题宽度或抬高消息气泡。
- 来源：用户当前任务、`docs/设计方案/02-信息架构与导航.md`、`docs/设计方案/04-代理与聊天.md`。

## DEC-014：聊天内容渲染与流式交互设计先行

- 决策：聊天消息使用 GFM Markdown、安全 HTML 子集、KaTeX、Shiki 代码高亮和 Mermaid 内容块；消息布局使用 `Message`/`Bubble`，唯一滚动区使用 `MessageScroller`，运行状态使用 `Marker`。
- 流式：文本以带序号的 UI delta 追加；已闭合内容块保持稳定；用户离开底部后不强制自动滚动；Mock Mermaid 导出只提供前端反馈，不写入磁盘。
- 安全：原始 HTML 使用明确白名单清洗；禁止脚本、事件属性、危险协议、外部资源和 Mermaid 交互覆盖；渲染结果不写入 Zustand。
- 阶段：先完成设计文档和用户审核，审核通过后才新增依赖、安装聊天组件和修改 `frontend/src`；本轮不接真实模型、工具、文件或 Wails 后端业务。
- 原因：聊天内容渲染、流式稳定性和安全边界会影响消息状态、滚动、依赖包和后端适配，必须先统一规范。
- 来源：用户当前任务、`docs/设计方案/12-聊天内容渲染与流式交互.md`、shadcn/ui 官方聊天组件文档。

## DEC-016：聊天页面第一轮清理

- 决策：已进入会话后的聊天页面暂时移除审批工具卡、自动审批状态流、固定思考大纲和独立代码应用卡；保留 Markdown/代码/KaTeX/Mermaid、基础消息状态、全部消息操作和唯一 `MessageScroller`。

- 高级能力：多模型比较与上下文压缩的标题栏菜单和 Slash 入口保留，仅在用户显式触发时显示，不默认插入消息流。

- 原因：当前聊天页面混入了尚未形成业务方案的审批、工具、思考和应用创建 Mock，用户要求先恢复最小消息闭环，再单独讨论后续能力。

## DEC-017：新建任务快捷建议随机推荐

- 决策：快捷建议不再固定为四项；从独立数据模块内置的 200 条推荐中，每次新建任务页挂载时随机抽取 4 条，保证同一组不重复。
- 内容：每条推荐同时保存唯一 ID、标题、prompt 和匹配的 Lucide 图标，覆盖代码、构建、审查、调试、文档、数据、Git、界面、工作流与安全等方向。
- 交互：点击快捷建议只将 prompt 写入当前草稿，不直接发送，不调用真实模型或后端服务；页面停留期间不自动轮换。
- 原因：保持首屏探索入口的新鲜度，同时保留可预测的点击填充行为和本地 Mock 边界。
- 来源：用户当前任务、`docs/设计方案/04-代理与聊天.md` §3.1、UI-017。

## DEC-018：按区域提供右键菜单，取消工作区万能右键

- 决策：移除包裹整个主工作区的通用 `WorkspaceContextMenu`。知识库、应用、能力、任务、设置等管理页的无对象空白区不显示右键菜单；会话/项目、应用卡片、任务/能力行、文件树、文件页签等对象继续使用对象专用菜单。
- 文本边界：所有 `Input`、`Textarea`、contenteditable 和带选区的正文使用共享 Aestival 编辑/文本菜单；Monaco、文件预览、终端和聊天消息分别使用专用菜单。右键菜单中的复制动作优先作用于当前选区，无选区时仅在明确声明支持全文操作的区域提供全文动作。
- 原生行为：`App.tsx` 继续阻止浏览器原生 `contextmenu`，不恢复系统菜单；菜单项统一使用 shadcn `ContextMenu`、Lucide 图标和平台快捷键。
- 边界：本轮仅整理前端 UI 菜单与剪贴板 Mock，不接入真实文件服务、终端、模型、搜索或权限业务；已有侧栏与对象菜单不顺手改成全局菜单。
- 原因：全局万能菜单把不相关的创建、搜索、布局动作带入每个页面，且覆盖输入框、代码编辑器和可选中文本的正确交互；按区域拆分后才能让菜单内容与对象语义一致。
- 来源：用户当前任务、`docs/设计方案/03-全局交互与右键菜单.md`、QA-002。

## DEC-019：Monaco 编辑组采用单一布局树与全局唯一文件投影

- 决策：编辑器拆分、活动编辑器、组内预览和关闭行为统一由递归布局树驱动；顶部主文件页签只作为该树中已打开资源的唯一投影，同一文件不因多组打开而重复展示。
- 组内结构：单组不增加局部标题；拆分后每组只显示紧凑活动文件标题与组级动作，不渲染完整页签条。最多四组，支持向右/向下拆分和比例调整，本阶段不实现拖拽重排。
- 文件行为：文件树默认打开到活动组；临时预览按组替换，编辑后自动固定；同一文件可在多个组中打开并共享工作副本。关闭组不把文件合并到相邻组，最后一个脏引用关闭时才确认保存。
- 响应式：窄窗口只显示活动组但保留完整布局树，恢复宽度后按原结构恢复。
- 原因：旧实现让顶部文件、活动文件和拆分组相互写入，容易产生重复页签、空组、不可控关闭与 Diff 状态循环；单一状态源可以使连续点击具有确定结果并可用纯状态测试覆盖。
- 来源：用户确认的 Monaco 拆分重构执行计划、`docs/设计方案/09-工作区面板与文件预览.md` §4.4、UI-019。
- 状态：用户验收否决，已被 DEC-020 替代；全局唯一文件投影、拆分组紧凑标题、四组上限和窄窗隐藏非活动组不再作为实现依据。

## DEC-020：Monaco 编辑组采用 VS Code 式独立交互

- 决策：每个编辑组拥有完整且独立的页签顺序、活动页签、预览页签、焦点、光标和滚动位置；主编辑组的“聊天”页签固定第一项、不可关闭、不可拖动，其他组不复制聊天。
- 拆分：向右或向下拆分只复制当前活动文件。文件树只向当前焦点组打开文件；切换任一组的页签不影响其他组。
- 拖动：页签支持组内重排、跨组移动和按修饰键复制；目标组已有同一资源时激活已有页签并移除来源。拖到编辑内容边缘创建新组，边缘热区不得覆盖页签栏。
- 内容模式：Markdown 源码、预览和并排预览属于同一文件页签内的模式，不建立多级文件页签；Diff 作为组内独立编辑器输入。
- 状态：递归布局树只描述编辑组结构和比例；各组状态与共享文件 Buffer 分离。共享 Buffer 允许多组同步内容，但 Monaco 视图状态保持独立。
- 边界：当前只实现前端 Mock 工作副本、Diff、全语言高亮和本地基础补全；不接 LSP、真实文件读写、历史版本或后端协议。
- 原因：UI-019 的全局资源投影和组间联动偏离 VS Code 的真实编辑组模型，导致用户无法预测拆分、切换、焦点打开和拖动结果。
- 来源：用户对 UI-019 的验收反馈、UI-020、`docs/设计方案/09-工作区面板与文件预览.md` §3/§4.4。

## DEC-021：项目工作项独立建模并由人类控制完成态

- 决策：项目工作项与现有定时任务使用独立类型、状态、服务和审计事件；每个项目固定使用待处理、处理中、受阻、待验收和已完成五种状态，作废作为生命周期而不是第六列。
- 权限：AI 与人类可创建、编辑、排序并在前四个状态间移动；只有人类可以从待验收确认完成，也只有人类可以重新打开、作废和恢复。AI 的越权命令必须被策略层拒绝并记录原因。
- 表面：主内容看板和右侧面板共享任务与审计快照，但日期范围、看板/甘特模式和选中状态分别保存；项目看板只允许作为右侧面板，不进入底部面板。
- 边界：首版使用内存 Mock Adapter 和只读甘特图，不伪造 Wails 持久化、真实 AI 规划、任务依赖、关键路径或资源负载。
- 原因：项目规划需要能被 AI 读取和辅助维护，同时必须保留人工验收的最终控制权，并避免与定时调度任务产生状态和权限混淆。
- 来源：用户确认的 UI-021 实施方案、`docs/设计方案/13-项目看板与甘特图.md`。

## DEC-022：Office 样例采用本地预生成产物与统一文档查看器

- 决策：PDF 在浏览器内由懒加载 PDF.js 直接解析；Word 与 PPT 的真实样例在开发期转换为本地 PDF，Excel 在开发期生成安全工作簿 JSON 和保真打印 PDF，产物随仓库提交。所有文档从文件树进入当前焦点编辑组，每个编辑器实例独立保存视图状态且只占一个文件页签。
- 安全：运行时不调用在线 Office 服务，不执行 PDF 脚本/表单、Office 宏或外部资源；PDF 对象、Canvas、二进制和生成 HTML 不进入 Zustand。未登记产物的 Office 文件必须显示明确不可用状态。
- 边界：首版只读；PPT 为静态放映，Excel 图表只在打印预览呈现。任意 Office 文件的实时转换、缓存、失效检查和文件读取留给未来 Wails `DocumentPreviewAdapter` 实现。
- 原因：浏览器无法在不引入远程服务或高风险大型运行时的情况下保真解析任意 Office 文档；预生成真实样例既能验证完整 UI，又保持本地优先和诚实 Mock 边界。
- 来源：用户确认的 UI-022 实施方案、`docs/设计方案/14-文档预览.md`。
